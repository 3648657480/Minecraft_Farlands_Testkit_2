## 三、渲染架构的关键决定（改代码前必须知道）

1. **本地帧**：网格跑局部坐标 `local = worldSection - base`，base 是 2^22 段的整数倍
   （`WideRenderBase`）。世界身份只在 `SectionKey` 里。
2. **段原点**：`terrain.vsh` 自己减相机，所以 `ChunkPosition` 传**世界原点**（≤2^31）；
   本地帧建立后走「整帧本地空间」：`GlobalSettingsFarCameraMixin` 把传给 uniform 的相机
   换成它的小数部分（`CameraBlockPos` 变成 0），段原点改传 `world - cameraBlock`。
3. **剔除盒必须用世界坐标**：视锥是世界空间。把它改成相机相对会出现「静止正常、一转视角
   全消失」。
4. **编译入口只有 `LevelExtractor.allChanged()` 可靠**。用 `ClientLevel.setSectionRangeDirty`
   替代会导致「一个段都不编译」（已验证，见 2026-11-13 教训）。
5. **`STRICT_BAND`**（`farlands.client.strictBand`，默认 true）只应门控「Y 分页窗口」相关
   的 hack；不能门控「可见集重填」——fork 绕过了 `SectionOcclusionGraph.update`，没人重填
   就会整屏空。

## 五、为什么之前会「runClient 好、实机全是问题」

已逐项验证**不是**环境玄学：

- fork jar 与 loom 开发 jar：10952 个 class **CRC 逐字节一致**
- mixin：两侧 `-Dmixin.debug.verbose=true`，共同加载的 53 个目标类**注入集合 0 缺失**
- PCL 注入的 GC 参数（`+UseG1GC / MaxGCPauseMillis=50 / G1HeapRegionSize=32M /
  MaxHeapFreeRatio=40 / +UseCompactObjectHeaders`）套到 runClient：生成速率 25→28 块/秒，无影响
- `farlands.*` 参数两侧一致；JDK 都是 25.0.3；`isDevelopmentEnvironment` 无人使用

真正原因是**场景差异**：开发世界 `test7_01` 的远区块是 11-02 预生成的（只读不生成）；
实机是新世界现场生成；再叠加「建立帧时三连全量标脏」和「推流半径 5」。

标签时优先用宽值（注意：`saveWithoutMetadata` 的 long 写入只服务网络/组件路径，**不是**

## 十一、runClient vs 实机：同世界同相机 A/B（2026-11-13 傍晚）

**结论先行**：在"同一存档 + 同一相机 + autotest 固定角色状态"下，安装形态
（KnotClient + 真实 fork jar）与 runClient 在 2^53 的 `[RDIAG]` 计数逐项相同、画面同一地形。
**没有证据表明 mod 打包形态或 Knot 启动引入差异**；此前的"实机有问题"可由世界状态与相机解释。

**工具**：

```powershell

  -Mode dev|prod -Tag <名> -Seconds 200 -JvmArgs "-Dfarlands.autotest=true;..."
```

   不固定时两次跑可见集 592 vs 234，`uncompiled` 完全不可比。

- 不同世界 + 未固定相机：实机 `visible=592 / uncompiled=55`（`dirtyNull=55`，稳定 4 分钟）；

**仍开放**：`visible=592 / 55 段常驻 UNCOMPILED`（数据存在、`dirtyNull=55`）是

判断是剔除范围还是脏标记覆盖问题。若 PCL 实机仍有症状，需要具体步骤/截图。

玩家留在 survival 被挤出传送点、漂移 60 格并跨过 2^31 缝，末端看起来像"实机渲染坏了"
（`visible=790 / uncompiled=221 / dirtyNull=221 / camSection=absent / pSec=-134217728`）。
autotest 已改为服务端 `ServerPlayer.setGameMode(GameType)`；复验后实机与 dev 在
