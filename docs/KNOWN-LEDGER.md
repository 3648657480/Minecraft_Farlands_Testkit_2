# 判定标准与已知台账（2026-11-18）

> 病因：项目一直在盲干，**没有"这是 feature 还是 bug"的书面标准**，
> 且"负责人已知"和"AI 已知"严重错位（AI 把推断/外部记录当成实测，负责人的事实停在对话里没进台账）。
> 本文件就是治这两条：**先定标准，再建台账；台账里每条都必须带来源标记。**

## 1. 四类判定（先分类，再决定修不修）

| 类别 | 定义 | 处置 |
|---|---|---|
| **现象 phenomenon** | 由坐标/精度/量化机制产生；不属于身份错、存档损坏、地形损坏 | **保留**，记录、刻画、可复现；不修 |
| **缺陷 bug** | 身份错（int 泄漏）、存档损坏、地形损坏、崩溃、日志洪水 | **必须修**，修完进五门 |
| **限制 limitation** | 已知不做/做不到的范围 | 不修，在发布说明里声明 |
| **未知 unknown** | 不确定属于哪类 | **不进代码**，先做探针；有数据再分类 |

**判定必须回答三个问题**（答不上来就是"未知"）：

1. **机制是什么？**（哪个坐标转换、哪个精度、哪个上限）
2. **影响的是身份/存档/地形，还是可观测行为？**（前者=缺陷，后者可能是现象）
3. **修掉它会不会掩盖现象？**（会 → 不修，或只做对照开关）

## 2. 来源标记（每条台账必须有且只有一个主标记）

| 标记 | 含义 | 能当证据吗 |
|---|---|---|
| `[MEASURED]` | 我们的探针/五门实测，附命令或日志 | ✅ 是 |
| `[OWNER-OBS]` | 负责人在实机亲眼看到 | ✅ 是（但需补条件/量化） |
| `[EXTERNAL]` | Wiki/社区/参考实现/他人记录 | ❌ 只作假设（R10） |
| `[INFERRED]` | 从代码推断，未测 | ❌ 只作假设 |
| `[FIXED]` | 曾经 `[MEASURED]` 的缺陷，已修且有回归证据 | ✅ 是（附修复提交/门禁） |

**铁律**：
- 没有标记的"已知"= 未知；
- `[INFERRED]`/`[EXTERNAL]` **不得**在文档或对话里被说成"实测/确认"；
- 用户的观察只能标 `[OWNER-OBS]`，不能改写成 `[MEASURED]`；
- 任何发布声明只能引用 `[MEASURED]`/`[OWNER-OBS]`/`[FIXED]`。

| 11-18 | "Alpha1 快出了" | 负责人感觉没有进展 | 完成定义先于进度叙事 |

## 5. 以后的硬规则

1. 任何"已知"进文档前，先给**类别 + 来源标记**；给不出就是"未知"；
2. 每轮开始先对齐台账：这轮要动的是哪条（K#）？它属于哪类？
3. 改动前先回答：这是修缺陷，还是掩盖现象？
4. 用户的口头观察 → `[OWNER-OBS]`，并补条件；AI 的推断 → `[INFERRED]`，默认不进代码；
5. 台账与 `PHENOMENA.md`/`ALPHA1.md` 冲突时，**以台账的来源标记为准**，改文档而不是改台账。
