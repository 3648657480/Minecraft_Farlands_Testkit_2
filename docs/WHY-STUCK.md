# 诊断：差在哪、为什么难产（2026-11-18）

> 目的：只做诊断，不派活。结论来自仓库统计、时间线与已有记录，不来自感觉。

## 0. 一页结论

- **差的不主要是"能力"，是成本结构**：源码改 vs 二进制打补丁；单版本 vs 活版本；
  一个目标 vs 三个目标（可玩 / 可达 / 现象研究）；有反馈 vs 零用户。
- **难产的机制不是"某段代码写不出来"，是"完成定义缺位 → 范围漂移 → 返工"**。
- 量化：8 周 583 次提交、213 个 mixin、70 个 patcher、36.9k 行 Java、36 份文档 5169 行、
  1 个预发布、**2 次下载**、游戏内复现并量化的现象 **0 条**（owner 目击 1 条：云，未量化）。

## 1. 关键数字

| 指标 | 数值 | 含义 |
|---|---|---|
| 提交 | 583（2026-09-23 ~ 11-18，56 天） | 平均 10/天，峰值 162/周（W44） |
| mixin | 213 | 要拦截的原版行为面 |
| patcher 类 | 70 | 字节码改写面 |
| Java 行数 | 36,936 | mod + patcher-core |
| 文档 | 36 份 / 5,169 行 | 记录密度高，也是维护成本 |
| 发布 | 1 个预发布，zip 下载 **2** 次 | 外部验证 ≈ 0 |
| 游戏内现象 | 目击 1（云），量化复现 0 | 使命指标未开张 |

## 2. 到底差在哪（vs mckuhei 1.19.2 64-bit）

| 维度 | mckuhei | G2 | 成本倍数（估） |
|---|---|---|---|
| 改法 | 直接改源码 | 打补丁的 jar + mixin（213） | ×5–10 |
| 版本 | 1.19.2（固定） | 26.2（会更新，补丁要跟） | ×N（每版重来） |
| 目标 | 让远方可用 | 可玩 + 可达 2^63 + 现象研究 | ×2–3 |
| 验证 | 自己玩 | 要外部用户/实机复现 | 不可控 |
| 产物 | 一个 mod | fork jar + mod + 探针 + 文档 + 发布包 | ×2 |
| 人手 | 一个人做一件事 | 一个人做三件事 | — |

**结论**：同样一句"让远方可用"，我们的实现成本高一个数量级；再叠加"现象研究"和"分发"，
是另一个数量级。**能力差距存在（源码级改动确实更省力），但不是主因**——主因是选了贵路径还叠加了多目标。

## 3. 为什么难产（根因排序，附证据）

### 3.1 完成定义缺位（主因）

- 直到 **2026-11-15** 才有 `ALPHA1.md` 的冻结边界；此前 `ROADMAP` 的 W1–W5 长期处于 🟡，
  没有"什么时候算完"的定义。
- 后果：任何一轮都可以无限延伸——2^31 → 2^53 → 远 Y → 2^63 → 2^88 → 又回 2^53。
- 证据：`EXPERIMENTS.md` 2626 行、`PHENOMENA.md` P0–P8，但"现象验收"条目直到本周才有。

### 3.2 交付形态选贵了（结构性）

- 二进制补丁要求拦截**每一个**原版行为：213 个 mixin、70 个 patcher、96 个诊断键。
- 副作用：mixin 优先级、BOM、打包、版本更新、双重转换，每一样都能吃掉一天。
- 对比：mckuhei 改源码只需改变量类型；我们改的是字节码里的每一个坐标转换点。

### 3.3 范围持续扩张（复利）

- 玩家 MVP → 光照 → 群系 → 实体 → 结构 → 远 Y → 2^63 → 2^88；
- 每次扩张都新增维护面，且旧面不会消失；
- 证据：W44 单周 162 次提交——这是"追赶"的形态，不是"收敛"的形态。

### 3.4 验证回路断裂

- 实验室数据丰富（P0/P7、2^54/2^56 对照），但**游戏内复现并量化的现象为 0**；
- 发布 zip 下载 2 次（含自己），内测无外部用户；
- 后果：没有"做对了"的信号，只有"又修了一个 bug"的信号 → 主观上永远在难产。

### 3.5 "修 vs 现象"没有落到默认值

- 全亮光照、整帧本地空间、`outline.wide`、实体 tick 护栏、流体护栏：默认值有的修、有的不修；
- P8 差点被当 bug 修掉（`outline.wide` 默认开就会掩盖它）；
- 后果：同一份代码里"保留现象"和"掩盖现象"并存，判断标准不一致 → 返工。

### 3.6 单人 + 活版本

- 26.2 一更新，70 个 patcher + 213 个 mixin 要重新验证；
- 没有 upstream 关系、没有协作者、没有社区；
- 这是可持续性问题，不是技术问题。

## 4. 什么不是原因（避免误判）

- **不是不会写代码**：能过五门、能到 2^63、能发布、能写探针——工程量真实存在。
- **不是没有理论**：阈值表、代码对照（`PHENOMENON-FROM-CODE.md`）、遮罩清单都有。
- **不是没有文档**：36 份 / 5169 行；文档甚至过多，本身也在消耗时间。

## 5. 三个致命选择（复盘用）

1. **选二进制补丁而不是源码分支**：成本 ×5–10，换来"可分发"；但如果目标是研究，分发不是必须的。
2. **第一天没定义"现象验收"**：导致 7 周内无法判断进展，只能靠"又修了什么"感知。
3. **同时追可玩 + 可达 + 可研究**：三个目标互相拖累；任一单独都更接近完成。

## 6. 代价清单（决策用，不是建议）

| 选项 | 需要的投入 | 能得到的 |
|---|---|---|
| 维持现形态继续 | 持续跟进 26.2；213 mixin 的维护；无外部验证 | 仍是"可玩 + 实验室数据" |
| 缩到"可观测现象包" | 1 条游戏内现象 + 记录（约 1 会话） | 项目第一次有"复现的现象" |
| 冻结 | 一份 freeze 报告 | 代码/文档/发布保留，价值 = 研究记录 + 工具 |
| 重做成源码分支 | 重新搭分支、放弃分发 | 成本降低，但仍是单人维护 |

## 7. 一句话

**难产不是因为难，而是因为"生出来"没有被定义**：项目一直在"修到能用"，
而"能用"从未被定义成一个可观测、可复现、可宣布完成的事件。
